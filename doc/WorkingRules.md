# 작업 규칙

## 적용 기준

현재 사용자의 명시적 지시를 우선한다. 공통 규칙 원본은 `D:\Source\Paper-Toss\Blueprints`다. 프로젝트의 실제 책임과 예외는 [아키텍처](ApplicationArchitecture.md)와 [앱 업데이트](ApplicationUpdate.md)에 기록한다. Bough는 솔루션 구성과 업데이트 흐름을 참고하며 외형을 그대로 따르지 않는다.

## 작업 범위

- 사용자가 명시적으로 요청하기 전에는 코드 생성·파일 수정·테스트 추가·빌드·실행을 하지 않는다.
- “개선하고 싶다”, “어떻게 하면 좋을까”는 방향 논의로 해석한다. 문제점, 최소 수정안, 장단점만 짧게 설명하고 결정을 기다린다.
- 작업 요청을 받으면 합의된 범위에서 진행하며 이미 승인한 작업을 다시 확인하지 않는다.
- 요청 밖에서 발견한 문제는 보고만 한다. 범위를 넓혀야 한다면 이유를 먼저 설명한다.
- 요청하지 않은 하위 에이전트나 별도 작업 세션을 만들지 않는다.

## 판단과 검증

- 요구사항과 현재 코드에서 확인한 사실만 근거로 삼는다. 확인하지 못한 동작이나 의도를 추측하지 않는다.
- 코드를 제거하거나 불필요하다고 판단하기 전에 호출 경로, 전달하는 값, 최종 소비자를 확인한다.
- 생성·호출부를 찾지 못했다는 이유만으로 불필요하다고 단정하지 않는다. “현재 사용 경로를 찾지 못함”과 “기능이 필요 없음”을 구분한다.
- 변경 전후에 사라지는 동작을 확인한다. 역할은 확인되지만 사용 여부가 불확실하면 제거하지 않고 근거와 불확실성을 보고한다.
- 모르면 질문한다.
- 별도 승인 없이 빌드·테스트·앱 실행과 변경 후 검증 도구를 실행하지 않는다. 승인된 Git 작업의 범위를 선택하기 위한 상태·차이·이력 조회는 수행할 수 있다.
- 배포 요청에 필요한 게시 산출물 생성은 배포 작업으로 수행하며, 앱 실행이나 테스트를 추가로 승인한 것으로 해석하지 않는다.
- 구현 완료, 사용자 실행 결과, 직접 수행한 검증과 배포 결과를 구분해 보고한다.

## 구현 원칙

- 현재 코드에 적용할 수 있는 최소 수정안을 우선한다. 요청받지 않은 일반화·공통화·패턴화·수명 주기 재설계를 하지 않는다.
- 요청하지 않은 식별자, 관리 단위, 계층, 객체를 만들지 않는다. 새 키·딕셔너리 축·매니저·팩토리·캐시·래퍼도 임의로 추가하지 않는다.
- 기존 기능이나 확장 지점을 검증 없이 제거하지 않는다.
- 작업 트리의 기존 변경은 보존하며 요청과 무관한 파일을 정리하거나 복원하지 않는다.
- 데이터 원본은 `Excel`이다. 변경 시 `ExportTools`의 공식 생성 도구를 사용하고 생성 JSON과 C#을 직접 수정하지 않는다.

## 코드와 답변 형식

- 설명은 짧고 핵심만 말한다.
- 변수명은 풀네임으로 쓴다.
- .NET 기본 라이브러리를 기준으로 하고 외부 라이브러리는 Dignus만 사용한다. 기존에 승인된 Avalonia와 플랫폼 호환 의존성을 임의로 추가·교체하지 않는다.
- C# 메서드 선언·호출의 인자를 자동 줄바꿈하지 않는다.
- 조건문에서 `&&`, `||`로 여러 조건을 묶지 않고 별도의 `if`문으로 작성한다.
- 네이밍·문구·식별자 수정 요청에는 설명이나 평가 없이 결과만 제시한다.

## 문서

- 작업 규칙·아키텍처·업데이트 문서와 릴리스 기록은 저장소 최상위 `doc/` 아래에 둔다.
- 사용자 안내는 최상위 한국어 `README.md`와 영어 `README.en.md`로 분리하고 상호 링크한다.
- README에 개발 구성이나 프로젝트 구조를 넣지 않는다.
- Unity의 물리 클릭 안내와 부모·자식 AND 조건 예제는 README에 설명한다. 이 안내를 위한 프로그램 내 문구나 UI는 추가하지 않는다.
- 설명 그림은 `doc/images/`, 릴리스 기록은 `doc/releases/`에 둔다.

## Git과 배포

- 커밋과 푸시는 각각 승인된 요청 범위에서 수행한다. 함께 요청됐다면 다시 승인받지 않는다.
- 담당 파일만 명시적으로 스테이징한다. 임시·빌드 산출물이나 다른 작업자의 변경을 포함하지 않는다.
- 기존 변경을 폐기하거나 force push·reset·rebase·restore·revert를 임의로 실행하지 않는다.
- 배포 형식은 Windows x64 자체 포함 단일 EXE다. 버전·자산 이름·무결성 정보는 [업데이트 계약](ApplicationUpdate.md)을 따른다.
- 완료 보고에 커밋 해시, 푸시 여부와 실제 릴리스 게시 여부를 구분한다.

## 작업을 마치기 전 판단

1. 요청 범위를 벗어난 변경이나 구조가 있는가?
2. 확인하지 않은 전제를 사실처럼 사용했는가?
3. 최소 수정으로 끝낼 수 있는데 일반화했는가?
4. 제거한 코드가 전달하던 값과 최종 소비자를 확인했는가?

해당 사항이 있으면 수정하거나 확인하지 못한 부분을 명확히 보고한다.
